# 상담사 상태와 초기 자동 배정 계약

요구사항정의서 25~27장·73장의 초기 구현 계약이다. 구현·배포·실제 수락 여부는 [작업 인계](handoff.md)와 [진행표](mvp-progress.md)에서 구분한다.

## 상태의 진실 원천

- 첫 접속은 OFFLINE이며 직원이 명시적으로 AVAILABLE(대기)을 선택한다. 직원이 선택할 수 있는 가용 상태는 AVAILABLE/AWAY/OFFLINE이다. RESERVED/RINGING/CALLING/AFTER_CALL은 서버의 배정 시도와 접수 상태에서 계산한다. 가용 상태를 바꿔 진행 중인 상담이나 후처리를 우회할 수 없다.
- 하나의 플랫폼 issuer·subject에 가용 상태 한 개를 저장한다. 여러 조직에 가입했어도 동시에 한 조직에서만 수신한다. 다른 조직의 폴링은 현재 조직을 자동으로 덮어쓰지 않으며 명시적 상태 전환이 필요하다. 진행 중인 상담과 후처리가 있으면 조직 전환을 거부한다.
- heartbeat의 마지막 수신부터 45초 동안만 자동 배정 대상이다. heartbeat는 직원의 수동 상태 선택 버전을 바꾸지 않는다. 상태 변경에는 별도 `stateRevision`을 보내 오래된 창의 명령을 거부한다. 로그아웃은 즉시 가용 상태를 OFFLINE으로 변경하고 미수락 배정을 해제한다.
- 수락한 CALL/TICKET이 PROCESSING인 동안 다른 상담을 수락하거나 자동 배정받지 않는다. CALL이 종료되면 AFTER_CALL이며 상담 기록을 완료해야 다시 가용 상태로 돌아간다. 직원이 AWAY/OFFLINE을 선택했다면 완료 후에도 그 선택을 유지한다.
- heartbeat 단절이나 API 재시작만으로 이미 수락한 상담·초안·후처리를 삭제하거나 다른 직원에게 다시 배정하지 않는다. 재접속 시 지속된 업무 상태를 복원한다. 실제 Media 재접속/종료 정책의 수락 검증은 별도 WebRTC 작업에 남아 있다.

## LONGEST_IDLE와 실패 처리

- 초기 방식은 LONGEST_IDLE이다. 가용 상태에 들어온 시각 또는 이전 상담/미수락 배정을 놓은 시각이 오래된 직원부터 고른다. 접수는 긴급/보통/낮음 우선순위와 접수 시각 순으로 처리한다. 대기 중인 CALL/TICKET에 적용하며 CALLBACK은 일정 확정 작업에서 처리한다.
- 현재 활성 조직·Membership·동적 역할의 `queue:accept`와 `queue:read`를 매번 확인한다. 아직 담당자가 없는 공개 접수는 공유 수신 대상이며, 이미 소유권이 있는 대기 업무는 두 권한의 SELF/TEAM/ORGANIZATION 범위를 함께 만족해야 한다. 예약 단계에서 접수의 소유권이나 작성 당시 팀을 바꾸지 않는다.
- 배정 제안은 30초 유효하다. 화면이 해당 제안을 받았다는 확인 전에는 RESERVED/OFFERED, 확인 후에는 RINGING이다. 고객 화면은 실제 수락 전까지 WAITING이며 Media 토큰을 받을 수 없다. 수락에는 현재 본인 배정의 ID를 보내야 한다. 미배정 대기 업무의 명시적 수동 수락도 같은 가용 상태·동시성·범위 검사를 거친다.
- 거절은 REJECTED로 남기고 즉시 다음 가능한 직원에게 제안한다. 30초 안에 화면 수신 확인이 없으면 MISSED, 확인 후 답이 없으면 TIMED_OUT이다. 두 경우 모두 직원 상태를 AWAY로 바꾸며, 직원이 다시 대기를 선택해야 새 수신 대상이 된다.
- 한 배정 회차에서 같은 직원에게 자동으로 다시 제안하지 않고 최대 10번 시도한다. 가능 직원이 없거나 모두 이미 시도한 직원이면 접수를 WAITING으로 보존한다. 10번 시도 후에는 자동 배정을 중지한다. 직원의 명시적 ‘배정 다시 시작’은 접수 버전을 검사하고 새 회차를 시작하며 이전 시도 이력을 유지한다.
- 직원 부재/로그아웃, 조직 전환, 권한 회수, 고객 취소는 각각 OFFLINE/ORGANIZATION_CHANGED/REVOKED/CANCELLED로 남긴다. 만료된 제안의 수락이나 거절, 타인의 제안 조작은 거부한다. 이미 성공한 본인 수락·거절의 재전송은 기존 결과를 유지한다.

## 저장·잠금·API

- `agent_presence`, `assignment_attempts`, Queue의 `routing_cycle`을 V10으로 추가한다. 기존 상담·고객·접수 본문을 이관하거나 자동 연결하지 않는다. 시도마다 대상 직원, 조직/접수, 제안·만료·수신 확인·종료 시각, 결과와 회차를 보존하며 Consultation 문서와 분리한다.
- PostgreSQL의 배정 전용 전역 행 잠금 → 조직 잠금 → 접수 잠금 순서로 가용 상태 변경·배정·수락·거절·다시 시작을 직렬화한다. 여러 조직에 속한 같은 직원을 중복 확보하지 않는 초기 DB 기반 구현이다. 활성 시도에 대해 접수당 하나·직원당 하나의 부분 unique index도 둔다. 관리자 권한 변경은 기존 조직 잠금과 조정하며 상태 변경/배정 재시작의 직원 명령은 감사 기록에 남긴다.
- 2초 주기의 worker가 미수신·만료·회수·취소를 정리하고 대기 접수를 배정한다. 각 조직 작업은 별도 트랜잭션이며 실패하면 로그를 남겨 다음 실행에서 다시 처리한다. 상태/heartbeat 요청도 해당 조직 배정을 갱신한다. Media 공급자 호출은 배정 트랜잭션에서 하지 않는다.
- `/api/agents/me` 조회, `/heartbeat` POST, `/status` PUT을 제공한다. 상태 응답은 현재 업무 상태·선택한 가용 상태·선택 버전·활성 조직·heartbeat 만료·본인 제안 정보를 포함한다.
- 대기열 응답은 기존 접수 필드를 유지하고 `offer`, `canAccept`, `routingPaused`, `attemptCount`를 추가한다. `/api/queue/{code}/accept`, `/reject`, `/restart-routing`, `/attempts`로 수락·거절·다시 시작·최근 100개 시도를 조회한다. 시도 조회에는 현재 접수 조회 범위를 적용하며 다른 조직의 ID로 조회할 수 없다.
- 새 수락 계약은 화면의 서버 상태·배정 ID 연결이 필요하므로 웹과 API를 함께 검수·배포한다. 백엔드 빌드 완료만으로 기존 개발 웹에 단독 반영하지 않는다.

## 상담사 화면 연결

- 상단 수신 상태는 서버 응답을 표시하고 AVAILABLE/AWAY/OFFLINE 선택에 현재 수동 상태 버전을 보낸다. 상담/후처리 중에는 AVAILABLE 선택과 다른 요청 수락을 차단한다. 화면 수신 상태 조회가 실패하면 재조회 안내를 제공하며 고객·과거 기록 탐색과 초안은 유지한다.
- 본인에게 유효하게 배정된 제안만 큰 수신 모달로 표시한다. 화면에 실제 표시한 시도 ID를 다음 heartbeat에서 확인하고, 수락·거절도 해당 ID를 보낸다. ‘대기열에서 확인’/Escape는 해당 제안만 숨기며 거절하거나 유효 시간을 늘리지 않는다. 같은 요청에 새로운 시도가 생기면 다시 표시한다.
- 대기열에서 현재 배정 대상·수신 확인 여부와 최근 100건의 배정 시도를 별도로 확인한다. 권한이 있는 직원은 배정 없는 대기 업무를 표시 버전으로 명시적으로 다시 시작하며 이전 이력을 보존한다. 조회 실패는 재조회할 수 있고 요청 변경 시 이전 조회를 취소한다.
- 다른 조직 창의 heartbeat가 충돌하면 현재 서버 상태를 확인하고 직원이 ‘현재 조직에서 대기’를 선택해야 수신 조직을 바꾼다. 설정의 명시적 조직 변경은 서버 상태 변경을 먼저 확인하며 진행 중인 CALL/TICKET·후처리가 있으면 차단한다.
- 상태 선택은 모바일에도 유지한다. 1023px 이하 화면에서 문서 영역 최소 높이를 확보하고 작업 영역의 세로 스크롤로 하단 저장/완료 버튼에 접근한다. 실제 합성 계정 검수에서 375×812 본문 178px, 768×1024 본문 203px, 가로 넘침 없음과 44px 동작 버튼을 확인했다. 실제 플랫폼 첨부·두 사람 음성 수락은 별도 검증이다.
