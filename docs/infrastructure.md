# 개발·운영 환경 기준

## 2026-10-04 개발 녹음 저장 구성

개발 Compose에 Redis 7.4와 LiveKit Egress 1.14.1, API/Egress의 `/recordings` 공유 볼륨(group 2000)을 추가했다. LiveKit 1.13.7에 내부 Redis 주소를 설정했고 기존 ICE/TURN 포트는 유지했다. audio-only Egress를 사용하며 Redis/Egress를 위한 외부 포트는 없다. 실제 양측 합성 음성을 캡처해 플랫폼 PRIVATE 업로드와 재생을 확인했다. `HELLOW_RECORDING_ENABLED`는 개발에서 기본 true이며 배포 보존 검사 중 false로 둔다. 저장이 확인되기 전 로컬 파일을 지우지 않는다. 녹음 권한·V16·검증·제약은 [상담 이력·녹음 계약](consultation-history-recordings.md)에 둔다. 운영 Compose/NAS 적용과 장시간·실기기 수락을 완료한 것으로 간주하지 않는다.

## 2026-10-03 인증·파일 설정과 배포 경계

[리뷰 수정 결과](review-repair.md)를 현재 부분 구현의 정본으로 읽는다. `PLATFORM_OIDC_ISSUER`와 `PLATFORM_OIDC_CLIENT_ID`, 첫 조직 생성용 `ADMIN_OIDC_ISSUER`/`ADMIN_OIDC_SUB`, 승인된 `HELLOW_ATTACHMENT_RETENTION_CODE`를 운영 계약에 맞춰 지정한다. 현재 플랫폼의 프로젝트 realm은 `app` access token에 `aud=account`, `azp=app`, `typ=Bearer`를 발급한다. Hellow는 서명·issuer·만료와 이 세 claim, 활성 조직 Membership을 검증한다. 플랫폼이 API 전용 audience를 발급하는 환경에서만 `HELLOW_API_AUDIENCE`를 설정해 더 엄격한 검사를 적용한다. ID token은 받지 않는다.

Compose의 `.env.dev` 주입을 이용하되 실제 비밀값은 커밋하지 않는다. 이전 조직 미지정 데이터는 격리되며 데모 시딩은 기본 비활성화다. V2/V3 migration과 개발 Hibernate update를 운영 이관 검증으로 간주하지 않는다. 개발 DB 전환은 별도 백업·복원 검증과 첫 조직 이관 후 수행하며 운영 NAS 적용은 이전 PUBLIC 파일 정리·실제 연동 수락을 거쳐야 한다.

사용자가 지정한 hellow 프로젝트의 환경·배포 기준이다. 실제 서비스와 배포 파일을 구현할 때 이 문서를 따른다.

## 실행 환경과 네트워크

- 개발 테스트와 운영 모두 Docker Compose로 관리한다.
- 외부 접근은 Nginx가 호스트 포트 `30160`으로 받는다.
- DB 등 추가 서비스에 외부 포트가 필요한 경우 `30161`, `30162` 순서로 하나씩 증가시켜 배정한다.

| 포트 | 서비스 | 용도 |
| --- | --- | --- |
| `30160` | Nginx | 웹 UI(`/`), 백엔드 API(`/api/`), LiveKit WebSocket 시그널링(`/livekit/`) |
| `30161` | PostgreSQL 17 | CRM 데이터베이스 직접 접근 (`5432`) |
| `30162` | LiveKit Server | 개발 시그널링 직접 접근 (`7880`). 외부 브라우저는 HTTPS `/livekit/` 사용 |
| `30163/TCP`, `30164/UDP` | 개발 LiveKit ICE | 공유기 외부 포트 → `192.168.0.55:7881/TCP`, `:7882/UDP` |
| `30165/TCP`, `30166/UDP` | 운영 LiveKit ICE | 공유기 외부 포트 → `192.168.0.93:7881/TCP`, `:7882/UDP` |
| `30167/UDP` | 개발 TURN 중계 | 외부 포트 → `192.168.0.55:3478/UDP` |
| `30168/UDP` | 운영 TURN 중계 | 외부 포트 → `192.168.0.93:3478/UDP` |

2026-10-03 사용자는 같은 삼성 인터넷 모바일에서 LTE 실패·Wi-Fi 연결 성공을 확인했으며 기존 음성 포트 전달을 설정하지 않았다고 밝혔다. 최종 선택은 **공유기 외부 포트만 개발·운영별로 나누고, 호스트 내부 포트는 기본 `7881/7882/3478` 유지**다. 개발 [LiveKit 설정](../infra/livekit/development.yaml)과 운영 [설정 템플릿](../infra/livekit/production.yaml)은 브라우저에 외부 포트를 광고해야 하므로 컨테이너 수신 포트도 외부 포트 번호를 사용한다. Docker가 호스트 기본 포트를 이 컨테이너 포트로 전달한다. 예: 개발 TCP는 공유기 `30163 → 192.168.0.55:7881`, Docker `7881:30163`, LiveKit `tcp_port: 30163`이다. 운영 Docker는 `7881:30165`, `7882:30166/udp`, `3478:30168/udp`를 사용한다. 내부 포트만 바꾸고 ICE 광고를 기본 `7881/7882`로 두면 브라우저가 잘못된 외부 포트에 연결한다. 운영 템플릿은 NAS 반영 완료 증거가 아니다. 개발 Compose의 새 설정 역시 통화 drain 후 적용/외부망 검수하기 전까지 준비 상태다.

LiveKit `use_external_ip`로 STUN에서 공개 주소를 찾고 UDP TURN을 함께 제공한다. HTTP reverse proxy만으로 ICE/TURN 포트를 전달할 수 없다. 호스트 방화벽도 해당 프로토콜을 허용해야 하며 공유기/NAS 설정은 저장소 변경만으로 적용되지 않는다. 이 구성은 UDP TURN이며 UDP가 모두 차단된 기업망을 위한 TURN/TLS 443은 별도 인증서·L4 경로 설정과 검증이 필요하다. 운영은 개발 기본 키를 사용하지 않고 API와 Media의 동일한 환경별 강한 키를 설정한다. 실제 모바일 LTE 수락 전에는 외부망 해결 완료로 보고하지 않는다.

| 환경 | 도메인 | 연결 대상 |
| --- | --- | --- |
| 운영 | `hellow.shnea.kr` | `192.168.0.93:30160` |
| 개발 | `dev-hellow.shnea.kr` | `192.168.0.55:30160` (개발 PC에서 localhost로 접근하는 서비스) |
| 로컬 테스트 | `dev-hellow.shnea.kr` | 개발 환경과 동일 |

DNS, TLS 종료 위치 및 인증서 관리 방식은 아직 정하지 않았다. 위 표는 지정된 연결 기준이며 실제 연결 검증 결과가 아니다.

## 운영 NAS 사양

사용자가 제공한 `shpark@shpark_NAS`의 명령 출력 기준이다. 에이전트가 서버에 접속하여 재검증한 결과는 아니다.

| 항목 | 확인된 값 |
| --- | --- |
| 운영체제 | Synology DSM 7.2, 빌드 64561, smallfix 0 |
| 커널 | `4.4.302+` |
| CPU 아키텍처 | `x86_64` |
| CPU 모델 | AMD Ryzen 5 PRO 4650G with Radeon Graphics |
| 전체 메모리 | `MemTotal: 32222600 kB` (약 30.73 GiB, 서버 전체 용량) |
| Compose 명령 | `docker-compose` |
| Compose 버전 | `v2.20.1-6047-g6817716` |

- 운영 이미지의 대상 플랫폼은 `linux/amd64`로 한다.
- 운영 Compose 파일과 배포 스크립트는 위 버전과 `docker-compose` 명령을 기준으로 작성하고 실제 NAS에서 검증한다.
- Docker Engine 버전, 가용 메모리 및 프로젝트별 자원 제한은 아직 확인하지 않았다.
- 제공된 출력의 작업 폴더는 `/volume2/homes/ttakji`이며, hellow의 배포 경로는 지정된 `/volume2/homes/hellow/`를 유지한다.

## 이미지 레지스트리

- 이미지 주소 형식: `registry.shnea.kr/프로젝트명-이미지명:태그`
- 이 프로젝트의 이미지 이름 접두사: `hellow-`
- 태그는 해당 이미지를 빌드한 Git 커밋의 SHA를 사용한다 (예: `a1b2c3d`). 커밋 메시지를 태그로 사용하지 않는다.
- 개별 이미지 목록과 빌드·게시 자동화 방식은 미정이다.

## Git 저장소

- 프로젝트 저장소: `https://github.com/shnea/hellow.git`
- 초기 브랜치는 `main`이다. 팀 브랜치·PR 정책 및 CI/CD 실행 조건은 미정이다. 커밋·push는 [개발·협업 원칙](development.md)을 따른다.

## 환경 변수와 암호화

- 공개 상담의 신규 대기 요청 한도는 `HELLOW_PUBLIC_PENDING_LIMIT`(기본 조직당 100건)이다. 같은 요청의 복원/재전송을 차단하지 않는다. 고객 세션 만료 worker는 기본 활성이고 격리된 복원 검수 때만 `HELLOW_SUPPORT_CLEANUP_ENABLED=false`를 사용할 수 있다. 공개 세션 계약은 [공개 접수 계약](public-support.md)에 둔다.

- 개발 환경은 `.env.dev`, 운영 환경은 `.env.prod`로 분리한다.
- 두 환경 파일을 각각 SOPS + age로 암호화하여 Git에 저장한다.
- 평문 환경 파일과 age 개인키는 Git에 저장하지 않는다.
- 암호문 파일명, age 수신자 공개키, 개인키 보관·주입 위치는 구현 시 확정한다. 비밀값은 일반 문서에 기록하지 않는다.

## 운영 배포 구성

- 운영 배포 경로: `/volume2/homes/hellow/` (사용자가 지정한 `volume2/homes/hellow/`를 절대 경로로 표기).
- 운영 서버에는 배포·실행에 필요한 최소 파일만 둔다.
- 대상은 Compose 파일, 필요한 환경 설정, 필요한 경우 암호문 복호화 도구·절차, 마운트할 파일이다.
- 운영 실행 이미지는 위 레지스트리에서 가져오는 구성을 기준으로 한다. 프로젝트 전체 소스와 개발용 의존성을 운영 배포물에 포함하지 않는다.
- 서비스 구성, 마운트 목록, 배포 명령, 상태 확인·복구 절차는 실제 구현 시 정한다.

## CI/CD 배포 대상 선택

- 확정 요구: 독립 배포 가능한 특정 서비스만 선택하여 배포하거나 전체 서비스를 배포할 수 있어야 한다.
- `user배포`, `all`은 사용자가 제시한 동작 예시다. Git 태그 문법·커밋 메시지 규칙·수동 입력·자동 실행 조건은 아직 확정하지 않았다. `user` 서비스 자체의 신설 요구도 아니다.
- 배포 대상 선택과 이미지 버전을 구분한다. 이미지 태그는 기존대로 해당 빌드의 커밋 SHA를 사용한다.
- 선택하지 않은 서비스는 선택 배포의 이유만으로 재시작·재배포하지 않는 것을 목표로 한다. 공통 모듈·DB/API/Event 변경으로 동시 반영이 필요한 경우 영향 범위를 먼저 판단한다.
- 서비스 이름 허용 목록, 잘못된 대상 거부, 공통 변경의 빌드 범위, 마이그레이션 순서·호환성, 상태 확인·롤백은 CI/CD 상세설계에서 정한다.
- 실시간 상담·Media의 선택 배포에는 기존 통화의 Draining 또는 검증된 재연결 정책을 함께 적용한다.

## 현재 상태

2026-10-04 개발 Compose·Nginx와 개발 도메인은 실행 중이며 API `6a5b73d`·웹 `8b42e83`, DB Flyway V22다. F01 통계/차트·목록 디자인 이후 F02 고객 채팅을 API/웹에 반영하고, 채팅 말풍선 좌우 배치는 웹만 선택 반영했다. F02 신규 백업·복원 V21→V22와 실제 DB의 기존28개 테이블 모든 행·기존 열 hash 보존, health·외부 공개 경로200·새 채팅 번들과 접근 차단을 확인했다. 이후 웹 선택 반영에는 새 백업·진행 통화/채팅/이관0·공개 CSS·미선택 서비스 이미지/시작 시각 보존을 확인했다. DB·Media/Redis/Egress는 재시작하지 않았다. 기존 계정의 새 통계/현황 권한은 자동 부여하지 않으며 관리자 설정과 실효 범위를 따른다. 실제 실행 버전·시각·증거·남은 수락은 [작업 인계 기록](handoff.md)에 둔다. 암호화된 환경 파일과 배포 자동화, 운영 NAS 배포는 아직 검증하지 않았다.
