# Hellow 개발 검증과 운영 배포 인계

2026-10-04 기준. [AI 인계서](ai-development-handoff.md)와 [기능 명세](remaining-feature-specs.md)의 실행·완료 기준이다. 명령은 기존 계약을 확인하고 해당 작업에 필요한 것만 실행한다. 이 문서 자체가 운영 변경이나 비용 사용을 승인하지 않는다.

## 1 작업 시작 절차

1. `AGENTS.md`, workflow·golden-path, 최신 handoff와 현재 Git diff를 읽는다.
2. 작업 ID와 범위를 확정한다. 확정 요구·제안·미정 정책을 구분한다. 이번 사용자가 지시하지 않은 다른 기능으로 넓히지 않는다.
3. 관련 코드·테스트·migration·문서를 찾아 현재 구현을 확인한다. 문서가 오래됐다고 코드를 전부 다시 만들지 않는다.
4. 변경할 권한·데이터·상태·API·UI·외부 계약과 완료 조건을 짧게 제시한다.
5. 필요한 정책 결정만 질문하고, 답과 무관하게 진행 가능한 코드 조사·명세·mock 기반 작업은 계속한다.
6. 기능 단위로 구현→검증→인계→커밋/push한다. 기능을 여러 AI에게 나눌 경우에도 사용자의 위임과 현재 에이전트 규칙을 따른다. 공통 권한·migration·라우팅·page.tsx 변경 책임을 조율한다.

### 기술 및 실행 환경

- Windows PowerShell, 현재 작업 폴더 `E:\JetBrains\IntelliJ\hellow`.
- 서버: Java 21, Spring Boot 3.4.4, JPA, Flyway, PostgreSQL 17 계열. Docker 빌더는 Gradle 8.12 이미지이며 저장소에 Gradle wrapper가 있다고 가정하지 않는다.
- 웹: Next.js 16.3.8, React 19.2.8, TypeScript, Vitest. 버전은 해당 시점 package/lockfile이 정본이다.
- 미디어: LiveKit, Redis, Egress. 파일·인증·에디터는 SHNEA 플랫폼 계약을 사용한다.
- 새로운 패키지/공급자 계약이 필요할 때 현재 버전의 공식 문서를 확인한다. 이 인계 문서만으로 최신 SDK 사용법·가격을 단정하지 않는다.
- 비밀값은 `.env`/암호화 파일/허용된 비밀 저장소에서 주입하며 문서·로그·커밋에 기록하지 않는다.

### 실제 통화 수락 행렬

테스트 대상의 브라우저 버전·기기·네트워크·앱 SHA·시작/종료 시각을 기록한다. 두 브라우저 합성 음성을 실제 삼성 사용자 검증으로 표기하지 않는다.

| 조건 | 확인할 것 |
| --- | --- |
| PC 상담사 ↔ 모바일 Wi-Fi 고객 | 수락, 양방향 음성, 양측 시간, 음소거/해제, 종료/후처리 |
| 삼성 태블릿 Wi-Fi 상담사 ↔ 삼성 모바일 LTE 고객 | ICE/TURN 실제 연결, 마이크/재생, 장시간 안정성 |
| A 상담사→B 호전환 + 고객 모바일 | 고객 마이크 불필요 재요청 없음, 기존 연결 유지, B 확인 전 A 소유 유지, 성공 후 B 작성 |
| 호전환 거절·만료·B 연결 실패 | 고객 통화 보존/기존 담당 복구, 중복 활성/잔류 참가자 없음 |
| 브라우저 닫기/망 단절 후 30초 안 복귀 | 같은 통화 시작 시각 유지, 연결 복원, 중복 녹음/접수 없음 |
| 30초 이후 미복귀 | 서버 관찰에 따른 통화 종료, 상대 안내, 기록·후처리 보존 |
| Media 공급자 조회 장애 | 참가자 부재로 오인해 통화를 즉시 끊지 않음 |
| 실제 녹음 | 양측 음성, 끝부분, 장시간, 이관 구간, 권한별 재생, 실패 재시도 |

현재 실제 LTE 연결과 녹음 저장은 사용자 확인을 받았다. 남은 표는 모든 상황이 확인됐다는 주장을 피하기 위한 것이다. 네트워크 포트 변경으로 이미 해결된 원인을 다시 미해결로 단정하지 않는다.

## 3 새 기능의 공통 검증 기준

### 서버와 저장

- 조직 2개, 동일 subject/다른 issuer, SELF/TEAM/ORG, 권한 없음/회수, 비활성 조직·직원 fixture.
- 목록·총건수·검색 snippet·상세·첨부/녹음·Export·Job·실시간 이벤트까지 동일 접근 경계.
- 같은 ID 동시 생성, 같은 ID 다른 본문, 예상 버전 불일치, 수락/취소·종료/저장의 경합.
- commit 직전/직후 실패, worker 재시작, lease 만료, 외부 성공 응답 유실, 중복/역순 callback, 재시도 고갈.
- 원문·담당·팀·버전·감사·관계 건수 보존. 외부 전송이 있는 기능은 호출 횟수/비용 중복을 확인한다.

### DB migration

- 기존 데이터가 있는 PostgreSQL 복원본에서 Flyway 적용과 Hibernate validate를 확인한다. H2 통과만으로 PostgreSQL partial index·CHECK·잠금을 검증한 것으로 간주하지 않는다.
- 기존 컬럼 전부를 포함한 정렬 snapshot/hash와 건수를 비교한다. 새 컬럼만 비교에서 제외하되 기본값·backfill은 별도로 검사한다.
- backfill이 의도된 작업이면 변환 대상·기준·전후 차이를 별도 검증한다. hash가 달라졌다는 이유만으로 검사를 생략하지 않는다.
- 구 앱과 신 DB 호환, 롤백 전략을 기록한다. destructive migration은 별도 승인과 검증 가능한 백업/복원 없이 실행하지 않는다.
- 개발 Compose는 Hibernate validate 설정을 확인한다. `application.yml` 기본 update를 이유로 Flyway 밖 자동 schema 수정을 허용하지 않는다.

### 프런트와 브라우저

- 실제 API 연결/합성 API 여부를 명시한다. synthetic fixture는 UI 동작을 검증하며 실제 권한 서버·음성 성공을 증명하지 않는다.
- PC 넓은 화면, 1440px, 768px 세로/1024px 가로 태블릿, 375px 모바일을 시작점으로 사용한다. 실제 기기 CSS 폭/키보드/확대/desktop mode도 별도 확인한다.
- 빈/로딩/오류/성공/읽기 전용/미저장/충돌, 긴 고객명·직원명·본문, 바닥 저장·닫기 버튼, 키보드 이동·focus·터치 영역을 검사한다.
- 페이지 가로 넘침, 실제 스크롤 소유자, overlay hit-test, 브라우저 오류, 기존 입력 유지 확인.
- UI 변경은 `skills/impeccable/SKILL.md`와 연결 지침을 따른다. 기존 문맥·정체성을 유지하고 detector 통과만으로 시각 검수를 대체하지 않는다. 사용자 보류 결함은 별도 기록한다.

## 4 실행 명령

명령은 저장소 루트 PowerShell 기준이다. 로컬 권한·컨테이너 접근·외부 네트워크 제한을 우회하지 말고 필요한 승인 흐름을 따른다.

```powershell
git status --short
git diff --check
python scripts/verify-docs.py

# Windows 실행 정책 충돌을 피하기 위해 npm.cmd/npx.cmd 사용
npm.cmd --prefix frontend test -- --maxWorkers=2
npm.cmd --prefix frontend run lint
npm.cmd --prefix frontend run build

# Docker 빌더는 Java 21과 전체 Gradle build/test를 수행한다.
# 아래 태그는 검증 이미지이며 실행 중인 서비스 태그를 바꾸지 않는다.
docker build --target api -t hellow-dev-api:handoff-check .
docker build --target web -t hellow-dev-web:handoff-check .
```

`npx.cmd tsc --noEmit`은 frontend 디렉터리에서 실행한다. `gradle test`를 직접 실행하려면 설치된 Java/Gradle 버전을 먼저 확인한다. 모든 명령을 문서만 바꿀 때까지 일괄 실행하지 않는다. 문서 변경만이면 링크·형식·사실 검사가 기본이다.

### 결과를 남기는 방법

- API/DB 검사: 실행 명령, 테스트 이름·개수, migration 버전, 실패/재실행 이유, 원천 대비 결과.
- UI: 시나리오·계정 범위·viewport·앱 SHA, 캡처와 proof. 화면을 실제로 열어 주장한 상태가 들어 있는지 확인한다.
- 외부 장비: 실제 참여자/기기/네트워크와 결과. 브라우저 콘솔 성공 로그만으로 사람이 소리를 들었다고 주장하지 않는다.
- 증거에 토큰·연락처·실제 본문이 있으면 마스킹/접근 제한한다. 민감 증거를 Git에 넣지 않는다.

## O01 관측과 장애 감지

**현재:** Actuator health/info와 일부 업무 감사/애플리케이션 로그가 존재한다. 구조화 로그·분산 추적·기본 지표·알림·버전의 운영 연결은 미완성이다. 요구사항 47~55, 60장.

### 구현할 내용

1. 요청 Trace/Correlation ID를 만들고 API 응답·서버 로그·외부 호출·Job까지 연결한다. 외부 입력 ID는 길이/형식을 제한하며 권한 근거로 사용하지 않는다.
2. JSON 구조 로그에 service/env/version/traceId/operation/result/duration을 제공한다. 조직/업무 ID의 공개 수준을 정하고 전화번호·본문·capability·토큰은 마스킹한다.
3. 앱·보안 감사·업무 이력의 목적과 보존을 구분한다. 오류 추적에 request body 전체를 자동 수집하지 않는다.
4. 지표 후보: API 오류/지연, DB pool/lock, 배정 대기·중복 거부, 연결 성공/실패, cleanup 적체, 녹음 저장 실패·재시도, Job lag, 미배정 콜백 오래된 건, 저장소 용량.
5. Prometheus 등의 label에 고객/접수/trace ID를 넣어 cardinality를 폭증시키지 않는다. 집계 범위와 상세 로그 연결을 분리한다.
6. liveness/readiness/dependency 상태를 구분한다. 선택 AI/STT 장애가 Core 전체 liveness 실패로 이어져 반복 재시작하지 않도록 한다.
7. 배포 SHA·환경·시작 시각을 진단 가능한 안전한 endpoint 또는 관리 화면에 표시한다. 내부 비밀 환경변수는 포함하지 않는다.
8. 기준 문서의 OpenTelemetry→Prometheus/Loki/Tempo→Grafana 방향을 확인하되 사용 가능한 공용 관측 인프라를 재사용한다. 구현 필요성을 확인하지 않고 전체 별도 스택부터 설치하지 않는다.
9. 오류율·녹음 실패·작업 적체·용량 알림은 실제 담당자·전달 채널·임계치·해제 조건을 정한다. 수치는 현재 계측 후 확정한다.

### 완료 조건

한 테스트 요청의 웹/API/외부 호출/worker를 추적 가능, 예외와 비밀값 마스킹 확인, 실패를 주입해 지표·알림/해제 확인, 배포 SHA 일치, 관측 저장소 장애 중 핵심 상담 정상. 실제 운영 알림 발송 시험은 승인된 수신처만 사용한다.

## O02 운영 NAS 배포

**현재:** 개발 배포는 반복 검증됐지만 동일 기능의 운영 NAS 배포 완료는 아니다. 상세 환경은 [infrastructure.md](infrastructure.md)가 정본이다.

| 구분 | 현재 기준 |
| --- | --- |
| 개발 | PC `192.168.0.55`, `dev-hellow.shnea.kr` |
| 운영 | NAS `192.168.0.93`, `hellow.shnea.kr`, linux/amd64 |
| 운영 경로 | 실행 구성 `/volume1/docker/prod/hellow/`, 데이터 마운트 `/volume2/homes/hellow/` |
| 웹 진입 | Nginx 호스트30160, HTTPS에서 WebSocket·공개/직원 경로 처리 |
| 이미지 | `registry.shnea.kr/hellow-이미지명:커밋SHA` 기준. latest 단독 의존 금지 |
| 비밀 | SOPS+age 및 환경별 주입, 실제 값 Git 금지 |

현재 네트워크에서 외부 ICE/TURN은 개발30163/TCP·30164/UDP·30167/UDP, 운영30165/TCP·30166/UDP·30168/UDP를 사용하도록 정했다. 내부 호스트 기본 포트와 컨테이너 광고 포트 매핑이 다르므로 환경 문서를 그대로 대조한다. 공유기의 넓은 30001~30999 규칙이 세부 규칙을 가렸던 이력이 있다. 설정 파일만 보고 실제 LTE 도달성을 단정하지 않는다.

### 배포 절차

1. 운영 반영의 현재 승인 범위, 소스 SHA, 이미지, 환경, schema 목표, 영향을 받는 서비스를 확인한다. Git push 위임과 운영 배포 승인은 별개다.
2. 인증 issuer/client/redirect/audience, 파일 프로젝트·보존 코드·PRIVATE 정책, LiveKit/Egress/Redis, 볼륨/그룹, 실제 저장소 용량을 확인한다. 기본 개발 비밀값을 운영에 복사하지 않는다.
3. HTTPS·DNS·reverse proxy·실시간 연결·외부 미디어 포트를 확인한다. 사설망 hairpin 결과와 실제 LTE 결과를 구분한다.
4. 활성 통화·진행 이관·후속 업무·worker 상태를 확인하고 drain/배포 창을 정한다. 새 세션을 차단해 검사와 재시작 사이 경합도 관리한다.
5. DB·필요 파일·설정 백업을 만들고 복원본에서 새 migration·앱 validate·기존 데이터/권한 보존·새 제약을 확인한다.
6. 호환성이 필요한 API/웹을 함께 반영하되 선택하지 않은 다른 서비스를 불필요하게 재시작하지 않는다. DB/Media 변경은 별도 영향과 rollback을 준비한다.
7. 필요하면 worker를 중지한 검증 구간에서 실제 DB 보존을 확인하고 정상 worker를 재개한다. 재개 여부를 누락하지 않는다.
8. health/readiness, 로그인/공개 페이지/조직 조회, 승인된 시험 계정의 업무 흐름·실음성을 확인한다. HTTP200만으로 완료 처리하지 않는다.
9. 실패 시 원인을 보존하고 검증된 호환 버전으로 복구한다. DB dump를 덮어써 배포 후 신규 데이터를 날리는 rollback을 기본값으로 삼지 않는다.
10. 버전·migration·서비스 시작 시각·검증·백업/복원·미확인 범위를 handoff에 기록한다.

### 배포 자동화가 남은 이유

저장소에 완성된 CI/CD가 있다고 가정하지 않는다. `output/deploy-workspace-repair.py`와 브라우저 증거는 현재 작업 PC의 Git 제외 산출물이며 다른 AI의 clone에 없을 수 있다. 이 파일은 특정 V19→V20 검증에 묶여 있으므로 미래 배포에 무검토 재사용하지 않는다.

후속 구현은 승인된 환경·대상 allowlist, commit SHA, 백업/restore gate, 활성 업무 drain, migration 호환, health, 실패 복구를 재현 가능한 관리 스크립트/파이프라인으로 정리한다. 예전 인계에 언급된 명령이 실제 저장소에 존재하는지도 확인한다. CI 공급자와 자동 배포 trigger는 미정이다.

## O03 백업과 복구 운영

**현재:** 개발 변경 시 수동 백업·복원 검증을 수행했다. 정기 자동 백업과 운영 DR 완료를 의미하지 않는다. 요구사항 68, 77장.

- 대상 목록: PostgreSQL, 아직 업로드 확정 전 로컬 녹음, 플랫폼 저장 파일의 별도 책임/복구 계약, 설정·암호화 비밀·필요 인증 키, 업무 Job 상태. 재생성 가능한 검색/집계는 복구 원천과 재생성 절차를 기록한다.
- 정책: 백업 주기·보존·암호화·외부/별도 장애영역 복제·접근 담당·RPO/RTO를 정한다. 사용자 정책 없이 숫자를 확정하지 않는다.
- 자동 검증: 파일 크기뿐 아니라 checksum·복원·핵심 건수/관계·권한·녹음 fileId 접근을 확인한다. 백업 실패와 오래된 마지막 성공을 알린다.
- 사고 절차: 쓰기/발송 중지, 복원 시점 선택, 삭제 tombstone 재적용, 복원 뒤 외부 메시지/과금/녹음 작업 중복 방지, 안전한 worker 재개.
- 완료: 격리 복구 리허설에서 실제 복원 시간·누락 범위 측정, 외부 파일 접근·schema·권한·대표 업무 확인. 운영 DB를 테스트 목적으로 덮어쓰지 않는다.

## O04 성능과 장애 수락

**현재:** 기능별 동시성/복구 검사는 존재하나 서비스 전체 동시 수용량·SLO·대규모 장애 수락은 미완료다.

- 목표를 먼저 정한다: 조직 수, 활성 상담사, 동시 통화/채팅, 분당 접수, 저장 문서/녹음 크기, 보고서 기간. 근거 없는 ‘몇 명까지 가능’ 약속을 하지 않는다.
- 합성 부하에서 전역 배정 잠금 대기, DB query/connection, 폴링 요청량, 메모리, LiveKit/Egress 자원·업로드 적체를 측정한다.
- 상담 저장/권한/배정 정확성을 유지하며 병목을 수정한다. 측정 없이 MSA·메시지 브로커·캐시를 대규모 도입하지 않는다.
- 장애 주입: API 재시작, Media timeout, DB 일시 실패, Redis/Egress 중지, 파일 API 실패, 네트워크 단절, worker 중복 실행, 느린 client.
- 여러 인스턴스를 고려할 때 현행 DB 잠금/lease/유일 제약이 실제로 중복 부작용을 막는지 확인한다.
- 완료: 목표 대비 지연/오류·데이터 무결성·복구 시간·한계와 병목을 보고한다. 미달 목표를 UI만 정상이라는 이유로 통과 처리하지 않는다.

## 5 문서와 커밋 및 완료 판정

### 기능마다 갱신할 기록

- 해당 기능 계약: 상태·API·권한·중복·실패/복구·보존 정책.
- `docs/handoff.md`: 가장 위에 현재 버전·완료/남은 일·다음 시작점.
- `docs/ai-development-handoff.md`: 기능이 완료되면 ‘이미 구현’과 잔여 표를 함께 갱신.
- `docs/remaining-feature-specs.md`: 작업 ID의 실제 구현·검증 상태/새 계약 링크. 미래 설계 제안을 이미 구현된 API인 것처럼 두지 않음.
- golden-path는 핵심 변경과 관련 영역 링크만 반영한다. 같은 상세 계약을 여러 문서에 복제해 서로 다르게 만들지 않는다.

### 최종 점검

- [ ] 범위 밖 UI·업무 규칙·권한을 바꾸지 않았는가.
- [ ] 실제 구현·mock 검사·실기기·개발 배포·운영 배포를 구분했는가.
- [ ] 새 권한과 기존 직원의 migration 정책을 확인했는가.
- [ ] 원문·고객·녹음·초안·버전·관계를 보존했는가.
- [ ] 외부 비용/메시지/파괴적 변경이 승인 범위에 있는가.
- [ ] 실패·재시도·중복·권한 회수·재시작을 검증했는가.
- [ ] 문서 링크·Git diff·비밀/실제 고객 정보 혼입을 확인했는가.
- [ ] 큰 작업 단위를 한글 커밋하고 push했는가.
- [ ] 사용자 보고에 결과와 실제 남은 일만 정확히 썼는가.

사용자에게 확인이 필요한 최종 수락이 남으면 구현 완료와 수락 대기를 나눠 보고한다. 사용자 제보가 자동 검사와 다르면 제보를 미해결 근거로 기록하고 실제 조건에서 재현한다.
