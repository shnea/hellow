# 상담 이력·처리 대기열·통화 녹음

## 확정한 화면과 권한 (2026-10-04)

- 권한 이름과 Data Scope로 판단한다. 관리자라는 역할명으로 전체 조회를 허용하지 않는다. 전체 상담 이력은 `consultation:read`의 허용 범위, My 상담 이력은 그중 본인 범위다. 둘 다 저장 상담과 아직 저장되지 않은 접수를 포함하며 미등록·취소·미연결을 제외하지 않는다.
- 처리 대기열은 `queue:read`의 SELF/TEAM/ORGANIZATION 범위를 적용한다. 배정 전 접수의 예외는 `queue:accept`가 있고 자신에게 유효한 수신 제안이 온 경우뿐이다. 다른 대기 상담사에게 같은 접수를 일괄 공개하지 않는다. 조회 범위와 한 명씩 순차 배정하는 라우팅은 별개다. 기존 이관에 따른 소유권 변경·원문 접근 회수 계약은 유지한다.
- 별도 상담 이력 화면은 전체 너비 목록과 접수 날짜·이름·전화번호·처리상태·담당자 필터를 사용한다. My에서는 담당자 필터를 제외한다. 단일 클릭은 편집하지 않고 더블 클릭 또는 상세 보기 버튼으로 팝업을 연다. 과거 상담·고객 정보 수정과 변경 이력을 유지하고 목록의 조건·페이지·스크롤·초안을 보존한다.
- 워크스페이스의 기존 3단 화면은 유지한다. 오른쪽 통합 타임라인은 기존 더블 클릭 상세 팝업이며 현재 상담을 덮어쓰지 않는다. 처리 대기열의 이전 상담 편집과 별도 상담 이력은 구분한다.
- 시스템 설정은 같은 메뉴/수신상태 영역 안에서 이동한다. 사용자에게 보이는 티켓은 문의/상담으로 정리한다. 내부 `TICKET` 자료형은 유지하며 실시간 채팅 전환은 후속이다.

## 녹음 수명과 접근

1. API worker가 진행 중인 음성 상담을 발견해 조직·접수당 하나의 작업을 영속 생성한다. 양측의 실제 Media 연결과 마이크 송출을 확인한 뒤 LiveKit Egress로 서버 오디오 합성을 시작한다.
2. 녹음 시작 전 STARTING을 저장한다. 응답 유실 시 같은 방의 Egress 결과를 확인해 중복 시작을 피한다. 종료 후 OGG 원본을 공유 볼륨에 보관하고 플랫폼 PRIVATE 파일 업로드로 옮긴다.
3. 업로드 requestId는 작업 UUID로 고정한다. 청크 재개와 완료 응답 유실 복구를 기존 플랫폼 클라이언트로 처리한다. fileId를 DB에 확정한 뒤에만 로컬 원본을 제거한다. 네트워크 실패는 지수 지연 재시도하며 상태·오류 코드·lease를 보관한다.
4. 녹음 메타데이터는 해당 상담 조회 권한을 확인한다. 재생/다운로드는 여기에 독립적인 `recording:read`와 녹음 행의 SELF/TEAM/ORGANIZATION 범위를 함께 확인한다. 재처리는 `recording:manage`가 추가로 필요하다. 권한은 녹음 시작 당시 담당·팀을 기준으로 평가한다.
5. 목록에 플랫폼 fileId나 capability URL을 노출하지 않는다. 재생 요청마다 현재 권한을 검사하고 감사 기록과 `no-store` 응답으로 짧은 플랫폼 보기 주소를 발급한다. 상대 주소는 플랫폼 origin 기준으로 해석한다. 팝업을 닫거나 조직/권한이 바뀌면 오디오를 제거한다.

기존 역할/직원에 새 녹음 권한을 자동 부여하지 않는다. 권한 설정에서 필요한 `recording:read` 범위를 선택한다. 다른 직원 녹음 열람은 이 권한의 TEAM/ORGANIZATION 범위가 필요하며 상담 조회 범위도 충족해야 한다.

## 환경과 검증

- 개발 Compose: LiveKit 1.13.7 + Redis 7.4 + Egress 1.14.1. 내부 Redis와 녹음 공유 볼륨을 사용하며 새 외부 포트를 열지 않는다. API와 Egress는 group 2000으로 볼륨을 공유한다. 녹음 네트워크 작업은 업무 라우팅 scheduler와 분리한다. `HELLOW_RECORDING_ENABLED=false`로 worker를 중단할 수 있다.
- V16은 `call_recordings` 테이블/인덱스만 추가하며 기존 데이터와 권한을 바꾸지 않는다. 배포 시 기존 DB를 백업·복원하고 worker를 멈춘 상태에서 기존 전 행/열 hash를 비교한다. 개발 적용 결과는 [인계 기록](handoff.md)에 둔다. 운영 NAS에는 이 구성을 적용하지 않았다.
- 격리된 복원 DB에서 실제 Egress → CRM worker → 플랫폼 PRIVATE 저장 → 보기 주소 발급/원본 재생을 검사했다. 36.249초/196,849바이트 OGG에서 서로 다른 두 합성 음성 주파수를 확인했다. 업로드 실패 후 같은 작업으로 READY까지 복구했다. 증거 `output/recording-worker-proof.json`; 실제 고객 통화 녹음은 아니다.
- 서버 통합 검사: 녹음 시작 응답 유실/업로드 재시도/동시 claim/음성 미연결/상담 권한과 녹음 권한 분리/다른 담당·조직 차단. UI: 4개 viewport에서 목록·상세·설정, 명시적 열기, 저장 후 필터·스크롤 보존, 스크롤로 저장 버튼 접근을 확인했다. 증거 `output/history-list-ui/`, `output/history-finish-review.md`, `output/history-documentation.md`.

## 남은 실환경 수락·제약

- 새로 녹음한 통화부터 재생할 수 있다. 기존에 원본이 없는 과거 통화는 소급 복구할 수 없다. 양측 연결 전 종료/극히 짧은 통화는 녹음 원본이 없을 수 있다.
- 삼성 태블릿·휴대폰과 LTE의 실제 대화 재생, 장시간 통화/업로드, 통화 이관 중 녹음 연속성, 서버 장애 복구와 디스크 용량 운영은 별도 수락이 필요하다. Redis/Egress 결과를 잃은 장애의 모든 복구를 보장하지 않는다.
- 플랫폼의 오디오 보기 capability는 짧게 만료된다. 재생 주소 갱신으로 새로 발급한다. Safari 및 물리 기기 재생 검증은 아직 하지 않았다.
- 세션 실제 1시간 유지·전체 예약 lifecycle·모든 화면의 회전/가상 키보드·공통 통화 시간 등의 기존 잔여 조건은 [복구 체크리스트](workspace-repair.md)에 유지한다.
