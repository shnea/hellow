# 공개 고객 상담 접수 계약

## 공개 조직과 요청

- 고객 URL은 `/support?org={publicCode}`이며 개인정보·직원 인증 토큰을 넣지 않는다. 공개 조직 조회와 접수는 활성 조직을 서버에서 확인한다. 로고·색상·제목·안내·버튼 문구는 기존 공통 설정/조직 오버라이드의 유효 값을 사용한다. 홈페이지 버튼은 이 URL에 연결한다. 페이지 조회·접수 결과 조회만으로 Queue를 생성하지 않는다.
- 고객이 명시적으로 접수한 요청의 ID는 브라우저 `crypto.randomUUID()`로 만든 UUID v4를 사용한다. 서버가 형식을 검증하고 조직과 함께 기존 중복 키를 구성한다. 같은 조직의 동시 재전송은 조직 잠금 안에서 하나의 접수/고객 세션을 반환한다. 요청 내용 SHA-256을 보존하여 같은 ID로 내용을 바꾸면 409를 반환하며 이전 접수를 변경하지 않는다. UUID 대소문자는 정규화한다.
- `GET /api/support/request/{publicCode}/{requestId}`는 해당 명시적 요청의 결과만 복원한다. 아직 없는 요청은 404이며 Queue를 만들지 않는다. 다른 조직의 같은 ID로 기존 요청을 복원할 수 없다. 요청 ID와 고객 세션 ID는 복원용 비밀 값으로 취급하며 고객 화면 주소에 넣거나 일반 문서/로그에 기록하지 않는다.
- 조직별 공개 WAITING 요청 수에 `hellow.public-pending-limit`(환경 변수 `HELLOW_PUBLIC_PENDING_LIMIT`, 기본 100건)을 적용한다. 한도에 도달하면 신규 접수는 429이며, 기존 요청의 같은 내용 재전송과 결과 조회는 허용한다. 취소/처리로 대기 공간이 생기면 같은 요청 ID로 재시도할 수 있다. 직원 내부 업무의 생성과 별개다.
- 공개 입력의 이름·연락처만으로 기존 고객과 자동 병합하지 않는다. 고객의 공개 응답에는 세션/접수 ID·채널·업무 상태·담당 표시명·현재 대기 요청 수·세션 만료 시각만 제공한다. 원문/전화/직원 권한은 반환하지 않는다. 실제 우선순위·가용 인력을 반영하지 못하는 예상 초/대기 순번은 제공하지 않는다.

## 취소·종료와 만료

- 고객 세션은 신규 접수 시각부터 24시간 유효하며 조회/재시도로 연장되지 않는다. 만료된 세션/요청 ID로 조회·복원·취소·음성 토큰 발급을 시도하면 410이다. 조직 중지는 고객 세션 경로도 404로 차단한다. 무작위 세션 ID는 해당 접수에 대한 고객 조작 권한만 가지며 직원 OIDC 권한을 부여하지 않는다.
- WAITING 취소는 CANCELLED로 저장한다. 같은 취소의 재전송은 동일 결과를 반환한다. 취소와 상담사 수락이 경합해 이미 CALL을 수락했다면 통화를 종료해 CALL_ENDED를 반환하되, 직원의 PROCESSING/후처리·저장 기록은 보존한다. 완료된 접수의 취소 요청은 실제 COMPLETED 결과를 반환하며 다시 열지 않는다.
- 이미 담당자가 확인한 CHAT/TICKET은 고객의 음성 종료/취소로 바꾸지 않는다(409). 신규 공개 CHAT은 [고객 채팅 계약](customer-chat.md)의 전용 종료 명령으로 대화만 끝내고 상담 기록 완료는 별도로 처리한다. 과거 단건 문의는 기존 PROCESSING/COMPLETED 조회를 유지한다. 두 경로 모두 음성 토큰을 받을 수 없다. 음성 `/end-call`은 CALL의 실제 진행 상태에서만 종료하며 미수락 요청을 이 경로로 취소하지 않는다.
- 10초 주기 만료 worker는 조직→접수 잠금 안에서 만료 WAITING을 취소하고 수락 CALL의 종료 의도를 저장하며 신규 채팅의 종료 시각을 저장한다. 수락 TICKET과 상담/대화 원문을 삭제하지 않는다. 기존 Media cleanup worker가 저장된 종료 의도를 재시도하며 실제 참가자 연결 제거의 수락 검증은 WebRTC 작업에 남아 있다. ACD도 만료 WAITING을 배정하지 않고 현재 시도를 CANCELLED로 종료한다.
- V11은 만료 시각/요청 내용 hash를 추가하고 초기 개발 DB의 상태 CHECK에 누락된 CANCELLED를 허용한다. 기존 공개 세션에는 적용 시점부터 24시간의 전환 기간을 부여한다. 기존 고객·상담·타임라인 본문은 변경하지 않는다.

## 화면 연결과 검증 경계

- 화면은 명시적 접수의 원래 내용을 조직별 `sessionStorage`에 먼저 보관하고, 새로고침 때 GET으로 결과를 확인한다. 응답을 받지 못한 요청은 보관된 동일 ID·내용으로 결과 조회 후 필요한 경우에만 재전송한다. 결과를 알 수 없는 상태에서 새 ID로 접수하지 않는다. 취소/종료/만료 후 명시적 새 접수는 저장 정보를 비우고 새로운 ID를 만든다. 저장소 사용 실패 때는 요청을 보내지 않고 안내한다.
- CHAT 수락 화면은 신규 접수의 저장 대화·연결/처리 상태·담당자를 제공하고 마이크·Media에 연결하지 않는다. CALL만 연결하며 실패 때 접수를 유지하고 명시적 재연결을 제공한다. 종료 API가 실패하면 진행 상태와 연결을 유지한다. CALL_ENDED와 채팅 종료는 직원 후처리 완료로 주장하지 않는다. 서버에 저장하지 않는 만족도나 미검증 운영시간/대기시간·암호화 방식의 성공 문구를 표시하지 않는다.
- 백엔드 통합 테스트·실제 PostgreSQL·V11 복원 증거와 실제 프론트/플랫폼/음성 수락 여부를 구분하여 [진행표](mvp-progress.md)와 [작업 인계](handoff.md)에 갱신한다. 새 API 단독 배포로 이전 고객 화면에 누락된 대기시간을 표시하지 않도록 웹/API를 함께 검수·반영한다.
