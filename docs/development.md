# 개발·협업 원칙

## 작업 완료와 인계

- 큰 작업 단위가 완료되고 관련 검증을 통과할 때마다 커밋하고 `https://github.com/shnea/hellow.git`로 push한다. 이 범위의 커밋·push는 사용자가 지속적으로 위임했다.
- 큰 작업 단위는 요구사항·기능·수정 목적을 기준으로 하나의 결과를 검토할 수 있는 범위로 잡는다. 사소한 파일 수정마다 커밋을 나누지는 않는다.
- 커밋 전에 [작업 인계 기록](handoff.md)에 완료한 내용, 실제 검증 결과, 남은 일, 다음 시작점과 제약을 함께 기록한다.
- 검증 실패 시 관련 문제를 해결하고 다시 확인한다. 실행하지 못한 검증은 통과로 기록하지 않는다.
- push에 실패하면 로컬 커밋 여부와 실패 이유, 재시도할 작업을 인계 기록에 남기고 정확한 상태를 보고한다.
- 다음 작업을 시작할 때 인계 기록과 실제 파일·Git 상태를 함께 확인한다.
- 커밋·push 위임과 실제 서비스 배포 범위는 구분한다. 배포는 별도로 정한 기준을 따른다.

## 사람 친화적 소스 구조

AI가 작성한 코드는 사람이 직접 읽고, 흐름을 추적하고, 수정하기 쉬운 구조를 우선한다.

- 하나의 파일이나 클래스에 여러 책임을 몰아넣지 않는다.
- 관련된 로직은 함께 두되, 책임이 달라지는 지점에서 분리한다.
- 단순 전달만 하는 의미 없는 중간 계층이나 과도한 파일 분리는 피한다.
- 기능의 시작점부터 최종 처리까지 주요 흐름을 자연스럽게 따라갈 수 있어야 한다.
- `Helper`, `Common`, `Manager`처럼 역할이 모호한 이름보다 실제 책임이 드러나는 이름을 사용한다.
- 코드 줄 수를 줄이거나 추상화를 높이는 것보다 이해하기 쉽고 수정 위치를 예측할 수 있는 구조를 우선한다.

하나의 파일에 모든 것을 몰아넣지도 않고, 하나의 기능을 이해하기 위해 수많은 파일을 따라가게 만들지도 않는다. AI가 읽기 편한 코드가 아니라 사람이 직접 추적하고 수정하기 쉬운 코드를 작성한다.
