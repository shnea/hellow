# 보안·인증·권한·개인정보

필요시 확인: 입력 경계·인증·권한·공유·민감정보를 다룰 때.

적용 범위: 입력·비밀정보 처리는 해당 경계에서 검토한다. 계정·역할·개인정보 절차는 실제 필요할 때만 적용한다.

## 관리자 및 추가 기능의 접근 경계

- 현재 플랫폼 프로젝트 realm의 access token은 `aud=account`, `azp=app`, `typ=Bearer`로 발급된다. Hellow API는 플랫폼 issuer의 서명·만료, 설정된 client와 일치하는 `azp`, Bearer token type, 해당 audience를 함께 검사하고 `(issuer, sub)`의 활성 Membership·Permission으로 업무 접근을 제한한다. ID token이나 다른 client 토큰은 받지 않는다. 플랫폼에서 전용 API audience가 제공되면 이를 설정해 해당 audience도 확인한다. 이 계약은 실제 로그인·권한 회수 검증으로 수락한다.
- 최고관리자 식별은 `ADMIN_OIDC_ISSUER`와 `ADMIN_OIDC_SUB`를 함께 검증한다. issuer만으로 최고관리자를 판별하지 않는다. 기본 issuer 주소는 인증 서비스 계약 확인 후 정하며 일반 계정을 최고관리자로 만드는 기본값을 두지 않는다. 현재 두 설정은 비어 있으면 거부한다.
- 최고관리자는 공통 설정과 대상 조직의 관리자 기능을 수행할 수 있다. 조직별 작업은 대상 조직을 명시하고 수행자·대상·변경을 감사 기록으로 남긴다. 조직관리자는 자기 조직의 범위를 벗어나거나 최고관리자 권한을 부여할 수 없다. 마지막 조직관리자 제거 방지와 안전한 관리자 이관을 지원한다.
- 최고관리자의 조직 관리 권한을 고객 업무 데이터 무제한 접근으로 확장하지 않는다. 내용 조회·청취 등이 필요한 지원 접근은 원문 81장의 명시적 접근·감사 기준을 적용한다.
- 상담 상태 모니터링, 상담 내용 열람, 통화 청취는 독립 권한이다. 조직/팀 Scope를 서버에서 확인한다.
- 조직 공유 템플릿 관리와 개인 템플릿 관리 권한을 구분한다. 개인 템플릿은 작성자 소유이며 관리자라는 이유로 자동 열람·수정하지 않는다.
- 현재 공통 분류/템플릿 변경은 최고관리자, 조직 공유 변경은 대상 조직 관리자에게 허용한다. 개인 관리는 별도 `template:personal` 권한과 정확한 조직·issuer·subject 소유자 일치를 함께 검사한다. 역할 화면의 개인 관리 범위는 SELF만 제시하며 서버도 관리자/넓은 Scope에 관계없이 정확한 소유자를 검사한다. 상담 조회 또는 작성 권한으로 해당 조직의 실효 분류와 활성 공유/본인 템플릿을 읽을 수 있다. 공유 변경 감사에는 원문 본문을 넣지 않으며 개인 본문은 조직 관리 감사에 노출하지 않는다.
- 지식 원문·파일·검색·Vector·AI 응답에 동일한 조직/Scope 경계를 적용한다. AI는 사용자의 권한을 넘지 않으며 권한 없는 지식을 인용·노출하지 않는다.
- 내부 채팅은 조직과 대화 참여 권한을 확인하며 WebSocket·검색·첨부파일에도 적용한다. 탈퇴·권한 회수 후 접근을 차단한다. 관리자 지위만으로 모든 비공개 대화의 열람권을 자동 부여하지 않는다.

## 팀·역할·데이터 범위의 현재 계약

- 직원은 조직 안에서 한 소속 팀과 여러 역할을 가진다. 팀은 부모 관계를 가진다. 자기 자신·하위 팀을 부모로 지정할 수 없고, 활성 직원·하위 팀이 남으면 팀 비활성화를 거부한다. 다른 조직의 팀·역할을 연결할 수 없다.
- 역할은 기능별 `SELF`·`TEAM`·`ORGANIZATION` 범위를 가진다. 직접 권한의 범위와 활성 역할의 권한을 합치며 같은 기능에서는 더 넓은 범위를 적용한다. 역할만 사용하려면 직접 권한을 해제한다. 역할을 캐시하거나 토큰에 넣지 않고 매 요청에서 현재 DB로 해석한다. 팀 권한에는 활성 소속 팀이 필요하다.
- `SELF`는 같은 issuer·subject의 직접 담당 기록, `TEAM`은 본인 담당 기록과 현재 소속 팀 및 활성 하위 팀에 저장된 기록, `ORGANIZATION`은 해당 조직의 기록이다. 담당자·팀은 수락/작성 당시 저장하며 팀 이동이 과거 소속을 바꾸지 않는다. 담당자를 식별할 수 없는 과거 기록은 조직 범위에서만 보인다.
- 고객은 그 고객 자체의 담당 범위 또는 접근 가능한 상담/배정 기록을 근거로 조회·수정한다. 고객이 조회 가능해도 다른 담당자의 상담 내용이 자동 공개되지 않는다. 상담·타임라인·변경 이력·첨부 뷰 티켓은 각각 기록 범위를 검증한다. 목록은 조직·담당·팀 조건을 SQL에 적용한다.
- 미배정 WAITING 접수는 `queue:accept` 권한이 있는 직원에게 공용 수신 대기열로 제공한다. 수락 후 담당자·팀 범위를 적용하고 실제 처리와 미디어 토큰은 본인 수락 상담에 한정한다. 팀별 자동 라우팅은 ACD 단계에서 구현한다.
- 조직 관리는 조직 전체 범위가 필요하다. 직접 권한뿐 아니라 역할로 부여한 관리자도 마지막 관리자 보호에 포함한다. 조직 잠금 안에서 직원·역할 변경 후 실효 관리자 존재를 검증하며 실패하면 전체 변경을 롤백한다. 최고관리자에게 업무 데이터 접근을 자동 부여하지 않는다.
- 역할·Membership 회수는 다음 API 요청에서 거부하며 화면은 순차 폴링에서 최신 기능 권한을 반영한다. 기존 미디어는 제거 worker에서 실효 `queue:accept`를 검증한다. 실제 LiveKit 연결 제거 수락은 별도 실환경 검증 항목이다.
- 등록 전 이력의 후보 조회·연결·취소는 `customer:write`의 대상 고객/접수 범위와 `consultation:read`·`consultation:write`의 접수/상담/타임라인 범위를 함께 검사한다. 후보는 SQL에서 조직/범위/미연결/완료/연락처를 제한하고 원문 본문을 반환하지 않는다. 변경 시 현재 권한을 다시 확인하며 연결이 작성 당시 담당·팀을 바꾸거나 다른 기록의 내용 열람권을 확대하지 않는다. 현재 접수의 등록/연결도 정확한 업무 조직·담당과 범위를 검사한다.
